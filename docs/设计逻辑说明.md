## 0. 一句话概括整个项目

把几本 PDF 版的心血管指南变成能问的东西：用户问一句，程序从书里找出最相关的几段，
**先判断这问题库里到底答得了答不了**，答得了就交给大模型，并告诉他每句话出自哪本书的哪一块、
PDF 的第几页、归在哪一节；答不了就明确说不知道，不许编。

主链路一条，从左到右：

```
提问 → PHI 脱敏 → 查询扩展 → 向量通道(下限 0.45) ┐
                                                  ├→ 加权 RRF 融合 → 交叉编码器重排 → 截 8 块 → 邻居扩到 16 块
                       自建 BM25 关键词通道       ┘        ↑
                                          可答性闸门（看向量第一名 ≥ 0.60，不够整批不给）
                                                    ↓
                                          拼提示词(医疗合规约束) → 大模型 → 答案 + 引用行(书/块/页/节)
```

配套的三条支线：**入库**（PDF→正文→切块→判重→写库）、**评测**（61 题考卷 + 判分器）、
**运维口子**（`/rag/diag`、`/bm25/*`、`/rag/chunk`）。

下面十节，每一节都是链上一个环节，格式固定：**要解决的问题 / 难在哪 / 代码怎么做 / 量出来多少 / 还没做到的**。

## 1. 正文从哪来：PDF 里的字 ≠ 书的内容

**问题**：抽取这一步做不好，后面全链路都在垃圾上算相似度。

**难在哪**：指南 PDF 是给 printer 排版用的，不是给机器读的文本。三种翻车形态：
① 扫描件根本没有文字层；② 字体子集坏了，抽出来是 CID 乱码，看着有字数、实际全是鬼画符；
③ 同一份文件被反复丢进目录（网盘、微信、覆盖保存）。

**代码怎么做**（全在 [RagInitializer.java](../src/main/java/org/ragai/service/RagInitializer.java)）：
- 四级兜底：标准提取 → 调参数重抽 → 直接扫字节流 → Tesseract OCR。
- 乱码判据 `weirdRate()`（`:688` 附近，`WEIRD_RATE_MAX = 0.15`）：数非空白字符里
  **不属于**「中日韩文字 / 拉丁与希腊字母数字 / 文档常见标点」的比例，超 15% 判乱码并触发 OCR。
  语言无关是刻意的——早先版本按中文判，结果英文指南被误杀。另设有效字数下限
  `MIN_VALID_NONBLANK = 200`（`:686`）拦「几乎没抽到字」。
- 落库前 `sanitizeExtractedText()`：清控制字符、私用区字形、水印串、14 种连字符码点。
- 三层判重：① `file_hash` 相同 → 直接跳过，**连抽取都不做**；② 抽完正文再比 `content_hash` + 块数
  → 文件动了但正文一样也跳过（只回写 `file_hash`/`extract_version`）；③ 真要重灌先按 `source`
  删旧块，**删除条数 ≤0 直接中止写入**（`:417`），否则库里会出现同一本书两套 `chunk_index`。
  metadata 里那三个指纹在 `:638-642` 落进去。
- 热监听：Windows 复制文件会先 CREATE 再 N 次 MODIFY（文件只写了一半），所以
  `waitFileStable()`（`:1302`）等大小稳定才处理。

**量出来多少**：本库现在 4 份文件、501 块（`/rag/diag` 的 `stored_overview`）。抽取管线版本号
`extract_pipeline_version = 2026-10-12a`，写进每块 metadata——**管线改了会强制重抽**，
否则修好判重之后，旧库因为 `file_hash` 没变而永远不会重灌（`:794` 那条注释记的就是这件事）。

**还没做到的**：`ENTRY_DELETE` 没接，文件被手动删掉后，向量块和 BM25 倒排都留在库里（任务 #49）。

## 2. 怎么找得准：光靠向量不够

**问题**：用户说"坏胆固醇""血糖偏高""全家胆固醇都高"，书里写的是"低密度脂蛋白胆固醇"
「糖化血红蛋白」。字面不一样。

**难在哪**：这是两种**不同的失配**，修法也不同——
① 说法不同但意思能通：向量能扛，但对精确的数值/术语问法不稳；
② 说法里带术语、缩写、英文机构名：向量常常排在后面，而关键词检索一搜就中。
所以不是"再加一路检索"这么简单，得决定**两路怎么合、谁说了算**。

**代码怎么做**：
- [QueryExpander.java](../src/main/java/org/ragai/service/QueryExpander.java) 在**检索侧**把口语补成
  规范术语，另有中英文桥（WHO / 世界卫生组织）。注意：开关
  `rerank-use-expanded-query` 只管重排那一步用哪个查询串，**召回通道永远用扩展后的串**。
- 两路融合 [HybridRetrievalService.java](../src/main/java/org/ragai/service/HybridRetrievalService.java)：
  向量通道每路取同样多条（关重排时 `probe-size: 8`；开重排时抬到 `max(probe-size, rerank-window)` = 20，
  `:220` 起的 `hybrid()`），按加权 RRF 合：`score = Σ 1/(rrf-k + 名次)`，`rrf-k: 60`（`:42`）。
  用名次而不是分数，是因为向量余弦和 BM25 分**量纲根本不可比**（`:18` 注释写明）。
- BM25 是自建的两张 PG 表（`bm25_docs` / `bm25_postings`，`ON DELETE CASCADE`），
  分数在查询时的 SQL CTE 里现算——所以没有缓存要失效（[Bm25IndexService.java](../src/main/java/org/ragai/service/Bm25IndexService.java)）。

**量出来多少**：关键词那路必须降权。定权那次实测（58 道库内题、**术语扩展之前**）：**口语提问下
BM25 把答案块排到第 1 的只有 10.3%，向量 31.0%**，两路等权反而把向量已经排好的中段挤掉——
所以定成 `vector-weight: 1.0` / `bm25-weight: 0.4`。这是实测选的，不是拍的。
⚠️ 这两个数**当历史依据读**：它们是「单通道各自排第 1」的比例，现行检索级基线给的是融合后的名次
（口语组 Hit@1 37.9%），两把尺子不完全对齐，所以没拿新数去替换旧数——降权比例至今仍按那次实测生效，
没在新口径下重测过。

**还没做到的**：库只有 501 块，跨块推理（多跳）现在测不出来，多跳题等库大了再造（任务 #50）。

## 3. 关键词索引不能再"每来一份就全表重建"

**问题**：上一节那两张倒排表，原本是**每入库一份文件就全表重建一次**。

**难在哪**：全量重建的钱只跟"库里总共多少块"成正比，跟"这次来了多少"无关——文件越多越亏，
每一份都要替全部历史文件付一次钱。

**代码怎么做**：入库走 `refreshSource(这一份的路径键)`（[Bm25IndexService.java:115](../src/main/java/org/ragai/service/Bm25IndexService.java#L115)，
调用点 [RagInitializer.java:170](../src/main/java/org/ragai/service/RagInitializer.java#L170)）：
先 `DELETE ... WHERE source IN (这一份的路径键)`，posting 靠 `ON DELETE CASCADE` 跟着走，
再只读这一份重算写回。启动那一次仍走全量对账 `rebuildAll`，`/bm25/rebuild` 留手动兜底。
**关键是全量和增量共用同一个纯行构造函数 `Bm25RowBuilder`**——两条路各写一套，迟早算出两套行。

**量出来多少**：刷一份 73 块的文件 737ms（钱只跟这一份的块数成正比）；
501 块全量重建 13 次启动日志样本 1544~1876ms。写库等价性当场证过（不是只靠只读重算）：
真刷块数最小的那份 73 块，写前/写后全表快照对比——**这一份的 doc 行与 posting 多重集逐字节相同**，
其他三份 md5 校验和前后相同，全库 501/89207/501 不变，孤儿 posting=0、缺行=0
（证据 `scratch/g2_bm25_refresh.out`）。

**踩过的坑（值得记）**：最初量出"增量 2565ms 比全量还贵"，原因是探针用了
`DriverManagerDataSource`——**每条 SQL 新建一条连接**，一次发 40 条语句 × 本地 PG 握手 46ms ≈ 1.85s。
换成 `SingleConnectionDataSource`（等价 Hikari）后 643/737ms。**测耗时的探针必须和生产用同一种连接池**，
否则量的是连接开销。

## 4. 能不能答：找来一批 ≠ 里面有答案

**问题**：库里没有的东西，模型会一本正经地编出来。医疗场景这条最要命。

**难在哪**：判"有没有"需要一个可比的分数，而闸门必须在**融合之前**判——一旦 RRF 之后，
分数是名次凑出来的，不再是"像不像"。

**代码怎么做**：
- 两道线，分工不同：`vector-floor: 0.45` 只做向量通道的粗筛（低于它的块压根进不了池子）；
  能不能答由 `answer-floor: 0.60` 判——**只看向量通道第一名那条的余弦**
  （`hasEvidence()`，[HybridRetrievalService.java:213](../src/main/java/org/ragai/service/HybridRetrievalService.java#L213)），
  不够就整批不给上下文，直接走拒答。
- ⚠️ **重排分不参与"能不能答"**：gte-rerank 的分只用来排序。它的分数和向量余弦不是一回事，
  拿它当闸门等于换了把尺子却沿用旧刻度。
- 逐条 0.65 那套旧做法已废弃（理由写在 README「检索闸门」一节）。
- `mode=bm25` 纯关键词不作为生产模式：闸门要的是余弦，纯关键词模式会**自动降级成 `hybrid`**
  并启动打警告，评测口子（`/evaluation/recall?mode=bm25`）照旧可用。

**量出来多少**：这道闸门**拦不住"字面蹭到医学词"的超纲题**——实测"火星上有没有心血管病防治指南"
top1 = 0.6591 > 0.60 照样过；"中医针灸治疗高血压有效吗"在 demo 档也过。试过加第三道闸：按
「问题里的实义词有多少在库里出现过」（词面覆盖率）判，**被数据证伪了**：正常口语题这个比例低到
25%（"抽烟对血管到底坏在哪里"）、33%、40%、50%，而域外对照的肺癌题反而 100% 全覆盖
（证据 `scratch/termcoverage.out`）。df=0 的词几乎都是口语虚词，跟"库里有没有答案"无关，
**阈值之间没有间隙可分**。所以这层判断留给模型，代码不做假精确。

**还没做到的**：模型自己拒答是对的（旧日志逐条看过），但"该答的题被闸门误杀"这一侧没量过全量分布。

## 5. 找到的块不够长：重排 + 邻居扩展

**问题**：两个。① 融合池里正确答案不一定排第一；② 表格经常被切块劈成两半，
只给前一半模型就断章取义。

**代码怎么做**：融合池取 20 条（`rerank-window: 20`）成对送进交叉编码器重新打分 → 截
`chat-top-k: 8` → 再把**同名文件的相邻块**扩进来，上限 `max-context-chunks: 16`。
重排调用失败自动退回融合顺序（不能让一次外部服务抖动把问答搞挂）。

**量出来多少**：重排是**全项目收益最大的一处**——答案块 Hit@1 从 **39.7% 提到 58.6%**。
⚠️ 这两个数是**清洗前旧库（507 块）+ 旧块号**下量的，新库+新标注下同口径带重排的数字**还没跑过**
（补齐要 58 次向量化 + 58 次重排，任务 #20，属可选加项；见 README「检索级基线」那条订正）。
现在的现行检索级数是**不带重排**的 hybrid 基线：58 题 Hit@1 50.0%、@8 96.6%、@20 100%，MRR 0.660。
邻居扩展值不值，用零成本方式定案过（不重跑模型）：翻已花过钱的报告，65 次判分里有 **2 次**
（#45 靠第 11 块、#42 靠第 16 块）只能靠 9~16 号邻居段命中，前 8 段是 55 次。
答案块名次 ≥9 定义上不在重排后前 8 里，**砍成 8 块这两题必挂** → 结论：16 块留着。

**还没做到的**：跨块的题本身还没进考卷，所以"多跳能力"没被测过。

## 6. 答案得让人核对：引用溯源到块、到页、到节

**问题**：答案末尾原来只写文件名。那等于"我说的，你信吧"。

**难在哪**：页码**库里从来没存过**——入库时是整篇抽成一条文本流再切块，metadata 只有整份文件的
`page_count`。而且一本书的"PDF 第几页"和"页脚下印的页码"经常差一个常数（前面有封面、目录）。

**代码怎么做**（[PdfPageLocator.java](../src/main/java/org/ragai/service/PdfPageLocator.java) +
[SectionIndex.java](../src/main/java/org/ragai/service/SectionIndex.java) +
[RagReferenceService.java](../src/main/java/org/ragai/service/RagReferenceService.java)）：
- 引用行从"文件名"加到 `文件名（块号 3、4、12）`，块号就是 metadata 的 `chunk_index`，
  和考卷标注、日志里的 `chunk=`、`/rag/chunk` 是**同一套编号**。
- 页码**读的时候现算**：按页重抽一遍 PDF 正文、走同一套清洗、压掉空白拼成整篇，
  再拿库里那块文字做子串匹配看落在哪几页之间。按页结果按「路径+修改时间+字节数」缓存在内存（上限 8 份）。
- 另给一个零模型调用的核对口子：`GET /rag/chunk?file=…&chunk=…`
  （[ChatController.java:168](../src/main/java/org/ragai/controller/ChatController.java#L168)）
  一次查库 + 本地按页重抽，把那块原文、物理页、页上印的页码、归在哪一节读出来给人对。

**核心取舍——宁缺毋滥**：认不出来就明说认不出来，**绝不猜**。
- 匹配不上就写「定位不到」，不给页码；印码偏移认不出规律就只给物理页并说明原因。
  给错页码比不给更坏——人会照着去翻那一页。
- 章节号同理：标题闸门 + 大纲单调性检查 + "存疑就整行不给号"
  （`SectionIndex.describe()` 只写「章节号不给 + 原因」，单测 `SectionIndexTest` 断言那一行**不许出现任何数字**）。
- **「推荐类别 / 证据等级」决定不做**：表格压平后库里长这样
  `推荐类别 Ⅰ Ⅰ Ⅱa Ⅱa Ⅱa Ⅲ 证据等级 A B C B C A`——每条推荐和它的等级在抽取那一刻就已经对不上，
  从这种串里报"这条推荐Ⅰ类A级"就是编。要做得换表格感知抽取 = 重灌库，属最贵一档。

**量出来多少**：501 块全量扫描——**478/501 = 95.4% 配上章节号**（其中 4 块判存疑被扣住，
线上真给号的是 474 = 94.6%）、跨节 118 = 23.6%（所以输出是 `4.1 → 4.2` 这种**范围**）、
未配上的 23 块全是"第一个标题之前（封面/目录）"。印码偏移四份文件实测 +835 / +220 / +999 / −12，
501 块回读 **0 例偏移不一致、0 例印码回退**（证据 `scratch/f2_scan.out`、`scratch/page_printed_sweep.out`）。
⚠️ 早期 `scratch/f2_scan` 里那个"章节号只有 9.8% 可用"是另一回事（不同判据），别再引那个数。

**还没做到的**：句子级溯源（哪句话来自哪一块）没有；"模型是不是真用了引用"只有形状证据。

## 7. 医疗场景自己的两条红线：隐私和不诊断

**问题**：输入里可能带身份证/病历号；输出里可能替用户下诊断。这两条不是加分项，是准入项。

**代码怎么做**：
- 脱敏 [PhiDesensitizationService.java](../src/main/java/org/ragai/service/PhiDesensitizationService.java)：
  身份证 / 手机号 / 病历号 / 出生日期 / 银行卡号 正则打码。
- 审计 [PhiAuditService.java](../src/main/java/org/ragai/service/PhiAuditService.java)：命中后只往
  MySQL `phi_audit_log` 写**原文指纹(message_hash) + 接口 + 命中类型:条数**，四列，
  **原文和脱敏后文本都不落库、不打日志**。以前那行 `[PHI脱敏] 原始: …` 会把含身份证的原话打进控制台，
  那次打印本身就是一次泄露。`/rag/diag` 的 `phi_audit` 段用 `stores_raw_text:false` 把这层意思明写出来。
- 不诊断：提示词规则 4 点名禁用「诊断为 / 确诊为 / 你得了 / 你患有」；判分器
  （[EvaluationService.java:175](../src/main/java/org/ragai/service/EvaluationService.java#L175) 起）
  **按小句判**：小句既没人称也没条件标记（`QUALIFIER_CHARS` 那 16 个字）才算裸断定违规。
  早先用裸词表，误伤过 #37——答案原样引用指南里"可确诊为"那句被误判成违规。

**顺带一个真实 bug 链（值得在面试讲）**：库存查询工具**一直连的是 PostgreSQL**，而 `consumables` 表在 MySQL。
根因是 `@ConditionalOnMissingBean` 让 MySQL 侧的 JdbcTemplate 从未生成，PG 里没有那张表，
每次查询都抛 `relation "consumables" does not exist`，而**旧代码把异常一律吞成返回 0**——
模型于是永远答"缺货，建议联系采购"，看着还挺合理。修法两条：
① 显式注入 `businessJdbcTemplate`（新写服务用库必须 `@Qualifier` 点名数据源，这已是本仓库硬规矩）；
② 工具返回**带语义的一句话**，把「有货 N 件 / 库里没登记这个耗材 / 库存系统连不上 / 没给耗材名称」四种说法分开。
改没改对，看 `/rag/diag` 的 `inventory_db_probe` 打出的行数（本机现在是 `行数=3`）。

## 8. 凭什么说它做得好：考卷、判分口径和"别混着引"的数字

**问题**：RAG 项目最容易的是"感觉挺准"。要能报数，还得数字站得住。

**代码怎么做**：
- 考卷 [medical_test_set.json](../src/main/resources/eval/medical_test_set.json)（读它的只有
  [MedicalTestSet.java](../src/main/java/org/ragai/model/MedicalTestSet.java)）：**61 题 = 58 道库内可答
  + 3 道故意超纲的负样本**。同一组答案块问两遍——书面说法（事实查询/综合分析）和患者口吻（口语查询），
  两组 ground truth 完全相同（JSON 里就是同一个 `answerGroup`），这样能单独看出"口语措辞"这一维度的失配。
- 判分三条硬口径（改任何一条都会让历史数字不可比，所以三条都钉进了单测）：
  ① **准确性**：出处必须逐字命中标注好的答案块；相邻一块之差的只写"可能考卷漏标"的线索、
     判分仍按挂处理（`EvaluationService.neighborHint`）；
  ② **幻觉抑制**：负样本必须出现那句**固定拒答原话**（`RagReferenceService.REFUSAL_PHRASE`，
     提示词规则 2 和判分器共用同一个常量，所以改那句话不会闷声判挂）；
  ③ **合规**：按小句判定。
- 两层指标**口径不同、不可混引**：`/evaluation/recall` 只测"标注的答案块排第几名"（Hit@K / MRR），
  `/evaluation/retrieve` 看生产链路真召回了什么，端到端测整答。
  `/evaluation/select?only=` 是付费重测前的**零成本预演**（只数命中哪些题）。

**量出来多少**：现行基线 **2026-10-16 全量 61 题 = 60/61 = 98.4%**。唯一挂的 #37 后来定位成
合规判分的裸词表误伤，判分器改成按小句后过（那是判分口径修复，不是检索变好）。
历史上还有 90.2%、95.1% 两个数，**属换尺子前后的结果，不能读成退步或进步**——
这一点 README 里专门有一节讲清了。

**纪律（这块比分数更像工程能力）**：
- **162 条纯逻辑单元测试**，不连库、不打模型、几秒跑完，共 19 个类：
  判分器（`AccuracyJudgeTest` 12 / `ComplianceJudgeTest` 8 / `EvalNormalizeTest` 5 /
  `EvalPromptGuardTest` 5 / `EvalSummaryCaliberTest` 4 / `MedicalTestSetStructureTest` 6）、
  引用与溯源（`ChunkCitationTest` 12 / `PdfPageLocatorTest` 23 / `SectionIndexTest` 22）、
  检索模式与工具与审计与索引（`RetrievalModeGuardTest` 8 / `InventoryToolVerdictTest` 5 /
  `InventoryToolSchemaTest` 9 / `MultiHopRetrievalServiceTest` 5 / `PhiAuditRowTest` 7 / `Bm25RowBuilderTest` 7）、
  demo 档（`DemoExtractiveModelTest` 8）、入口、多轮与异步任务（`ApiKeyFilterTest` 8 / `ChatMemoryManagerTest` 3 / `EvaluationTaskServiceTest` 5）。
  它守的是"两边漂移"这类最阴的错：改了提示词没改判分器、改了引用行形状没改判据、
  改了 BM25 行构造导致增量删不回旧行、改了 `@Tool` 描述没改返回值口径、白名单漏了前端裸文件。
- 配置写错要**喊出来**：`app.retrieval.mode` 拼不认识的名字时，switch 会静默落 default＝按 vector 跑，
  以前日志还把配置值原样打出来看着像生效了。现在启动打警告、`describeMode()` 如实写
  `vector（配置=xxx，模式名不认识）`。
- `/rag/diag` 让状态可查（默认不重扒正文，深挖加 `?deep=true`）；这些探针都不打模型。

## 9. 让别人也跑得起来：一键试跑档

**问题**：这个项目写进简历，但别人 clone 下来跑不起来——只有你本机（有 key、有库、用 IDEA）能跑。
追问一句"我能跑吗"就露底。

**难在哪**：RAG 应用有两处外部依赖（embedding 服务 + 大模型）和两个数据库。要让人零 key 零安装跑起来，
又不能把整条链路 mock 掉——**全 mock 的 demo 等于没演示**。

**代码怎么做**：
- [pom.xml](../pom.xml) 补 `spring-boot-maven-plugin`：以前 `mvn package` 只出 thin jar，
  既不能 `java -jar` 也做不了镜像。
- `demo` 档（[application-demo.yml](../src/main/resources/application-demo.yml) +
  [DemoModelConfig.java](../src/main/java/org/ragai/config/DemoModelConfig.java)）
  **只替掉两处**，用 `@Profile("demo")` + `@Primary` 顶掉：
  ① 向量化 → 字符 2-gram 哈希向量（1024 维、L2 归一化；`String.hashCode` 是 JLS 定死的，
     所以换机器重跑不会让已有向量作废）；② 生成 → 抽取式假生成（从送进模型的上下文里按字面重叠挑 3 句原文拼回去）。
  其余**全是真代码**：检索、RRF、BM25、闸门、邻居扩展、引用溯源、PHI 脱敏与审计、判分器、`/rag/diag`。
- [Dockerfile](../Dockerfile) + [docker-compose.yml](../docker-compose.yml)：pgvector/pg17 + mysql:8.0 + 应用，
  一条 `docker compose up --build` 起整套；[docker/mysql-init/01-demo-consumables.sql](../docker/mysql-init/01-demo-consumables.sql)
  建 `consumables` 塞三行示例库存（**故意少塞一种耗材**，好让"未登记"那一态看得见）。
- [.dockerignore](../.dockerignore) 关键一行挡住 `application-local.yml`——
  Dockerfile 是 `COPY src src`，不排除就等于把百炼 key 打进镜像层分发出去。
- 知识库用仓库自带的两份**合成**示例指南（页眉明写"数值为编造，不可用于临床"），
  源 HTML 和重打脚本在 [data/samples/](../data/samples/)。

**量出来多少**（demo 档自己的实测）：24 题打 `/chat`（15 库内 + 7 超纲 + 2 个前端 chip）——
**15 道库内题答到点上 10 道，挑进答案的 45 句里 10 句是标题行/表头/示例页脚这类噪声；
7 道超纲题逐字拒答 4 道**。假向量分数分布：库内 top1 0.0641~0.4100、超纲 0.0478~0.1715，
**两组重叠**，所以 demo 档的 `answer-floor: 0.05` 只是"字面几乎不沾的题别浪费上下文"的下限，
和生产那两条 0.45 / 0.60 **没有任何对应关系**。

抽取器排序口径是**量了四档才定的**（同一 jar 换 `-D` 重启、24 题探针）：IDF 加权总量
**10/15 命中、45 句里 10 句噪声**最好，`idf÷√句长` 与 `idf²÷句长` **各 9/15、15 句**（两档打平），
原先那版「命中数²÷句长」**8/15、18 句**最差。四档答案留档：三档在 `scratch/variants/*.out`，
原公式那档在 `scratch/_c_answers.out`；后面这三个数是**用 `python scratch/rescore_answers.py` 拿现行判据
从存档答案重算出来的**（脚本顺带复现了 10/15、10/45 和两个 9/15、15，所以四档同一把尺子）。
结论是可复现的，但**过程中出过一次严重错误**：更早一版文档写"IDF 试过没变好"，
而那次对照的两份文件其实是同一个配置跑的（探针改了题目标签、旧输出被覆盖）——**等于没有对照组，
结论方向整个反了**。教训已写进注释：A/B 对照要先确认两份输出真来自不同配置。

**五个诚实边界**（README「快速开始」第一节也列了，这里不重复细节）：分数不可比、闸门拦不住医学词超纲题、
样本只有 24 题 6 块、**compose 从没在真容器里跑过（这台机器没装 Docker）**、假生成答案糙。
另有一条：本机验证是 `demo,local` 两个 profile 叠加 + 命令行显式指定数据源跑的，
而 compose 只激活 `demo`，所以 `${DEMO_*:默认}` 拼出的两条连接串和 `depends_on` 启动顺序**未真走过**。

## 附录 B：黑话 → 大白话

| 术语 | 大白话 |
|---|---|
| RRF 融合 | 两路各排各的名次，只看"谁在两边都靠前"，不比分数 |
| 交叉编码器 / rerank | 把问题和候选段**成对**再算一次，比单独编码准，但贵，所以只重排前 20 条 |
| BM25 / 倒排索引 | 关键词版搜索：哪个词在这块里出现、这本书里稀不稀有 |
| HNSW / pgvector | PG 里的向量索引与向量列，用余弦距离 |
| embedding | 把一段话变成一串数字，意思越近数字越像 |
| 可答性闸门 | 找来的东西里没有一条真的像答案，就整批不给模型，直接拒答 |
| chunk_index / 块号 | 一本书被切成小段后的编号，引用和考卷标注都指它 |
| 邻居扩展 | 把被切断的表格旁边那块也带上，凑够上下文 |
| PHI 脱敏 | 身份证、病历号这类先打码再往下走 |

## 附录 C：三个高频追问的短答

- **"你怎么保证不是幻觉？"** → 三层：闸门让"库里没有"变成显式拒答；提示词禁诊断措辞；
  判分器要求负样本必须逐字出现那句固定拒答原话，且准确性的出处必须命中标注的答案块。
  再加一句老实话：超纲但字面沾医学词的题，闸门拦不住，是模型自己拒的。
- **"效果怎么量？"** → 61 题考卷、三条硬口径、98.4% 现行基线；检索级和端到端两套指标分开引，
  换过尺子的那两个旧数字（90.2/95.1）标明了不可比；重排收益有检索级对照（@1 39.7→58.6），
  但要如实说一句：那组对照是清洗前旧库量的，新库+新块号下的同口径带重排数字还没跑（任务 #20）。
- **"为什么不用现成的 RAG 框架？"** → 用了 Spring AI 的 VectorStore/EmbeddingModel，但弃用
  `QuestionAnswerAdvisor` 改手动控制检索：因为要卡可答性闸门、要引用溯源到块/页/节、
  要自定义合规约束的 System Prompt——这些都得自己攥着检索结果才能做。
